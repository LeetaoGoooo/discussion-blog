    或者说根据我自己的经验，焦虑之前可以判断以下几点

    1. 自己公司是否有足够的 Context Memory 系统的建设，能让 AI 获取足够的 domain knowledge 吗？

    2. 是否有足够的 devcontainer 等基建，能够让 Agent 有隔离的自迭代的跑起来

    4. 是否有足够的 skill/memory 等共享机制来复用通用能力

    5. 数据仓库是否有足够的权限控制，可以实现满足 合规下的 AI 数据接入

    如果以上有三点都没有做到，那我觉得暂时不用担心自己被 AI 替代，因为替代你的成本会很高。

    简单分享下我是怎么花最少的钱，但是又非常重度、高频的依赖 AI coding 的。



    我目前的订阅是，最便宜的 copilot 和 codex。这两个的特点在于：codex 是按量付费的，而 copilot 是按次付费的。这个区别是最关键的，如果你更喜欢 cc，那么你可以把本文中的 codex 替换为 cc，一样的逻辑。



    而作为 coding，其实工作可以拆分为两大类型，我相信其他大部分文字工作也可以这么拆分：



    1. 计划阶段：此时会涉及非常高频交流，但是每次交流的内容都不多，你可以使用 codex 的最高思考模式，写下最核心的关键逻辑

    2. 实施阶段：这是广义的实施，包括收集资料、撰写文档、coding、testing、debug 反复调试 都可以视为实施。



    copilot 的按次付费，使它成为实施阶段的最佳性价比选择。发送一次 prompt 算一次费用，只要 agent loop 没有结束，期间一切的 tools 调用都不计费。只要通过 prompt 给它输入我们之前和 codex 聊好的 spec，接下来就让 copilot 吭哧吭哧的去把最脏最累但是没有特别高思考难度的活全部干完。



    具体怎么让 copilot（我最爱用 gpt-5.4） 能够不中断的，一次性干完最多活，这里面需要调试 copilot 的 instructions，具体就不展开了，各有各的方法。但是我这里推荐一下我的 remote MCP server https://mcp.laisky.com/tools/get_user_requests



    其中的这个 get_user_requests tool，相当于是在 MCP 上维护了一个 TODO list，而且是你可以动态编辑的 TODO list。你只需要在 instructions 里要求 copilot 频繁的，在每次子任务结束后，都去调用 get_user_requests，而且必须在连续两次调用 get_user_requests 为空后才能返回。你其实就拥有了在不打断 agent 一次任务的前提下，和 agent 沟通的能力，而利用这个能力，你就可以让 copilot 在一次计费里，干掉尽可能多的活。



    举个我的例子，极端情况下，我很可能一天只需要跑 3 次 copilot，中间会停两次是因为我要吃午饭和晚饭，没精力去盯着 get_user_requests 的 requests queue 了。我甚至经常跑出 copilot 的 tokens limit，估计很多人可能都不知道 copilot 还有limit 吧😂



    Copilot 还有个我非常喜欢的地方是，如果你把配额用超了，它可以自动转为按次计费，每一次请求约为 $0.03 USD，很实惠。



    如果你非常有钱，或者公司给无限的订阅资金，可以忽略这一条。和穷人们共勉。

    Reciprocal Rank Fusion（RRF）



    在做搜索系统或 RAG 时，经常会遇到一个问题：如果有多个检索器，应该如何把它们的结果合并？



    RRF 是一种非常经典的融合方法，它的核心思想很简单：一个文档在多个排序结果里排得越靠前，它最终的分数就越高。



    RRF 不直接使用原始分数，而是只使用“排名”。它的公式是：



    score = ∑ 1 / (k + rank)



    其中 rank 是文档在某个排序中的名次，k 通常取 60。



    为什么只看排名？因为不同检索器的分数尺度往往不同。比如 BM25 的分数可能是 8.73，而向量相似度可能是 0.82。如果直接相加，很容易失真。RRF 通过使用排名，绕开了分数尺度不一致的问题。



    在实际系统中，RRF 常用于融合不同“视角”的召回结果。比如：



    * embedding 负责语义召回，扩大覆盖范围

    * BM25 负责关键词匹配，保证强实体命中

    * RRF 将两者融合，让多个系统都认可的文档更靠前



    这种做法的好处是稳健。它更偏向于在多个系统里都表现不错的文档，而不是只在某一个系统里极端靠前的文档。



    在 RAG 场景中，这一点尤其重要。因为如果正确文档在召回阶段被挤掉，生成模型就无法基于真实证据回答，风险远大于多带入一两篇一般相关的文档。



    RRF 中的参数 k 决定融合的“激进程度”。k 越小，前几名的优势越大，系统更激进。k 越大，排名差距被压缩，系统更平滑稳定。工程实践中常用 k = 60，以获得更稳健的召回表现。



    如果某个检索器明显更强，也可以通过调整候选数量比例来改变融合效果，比如 embedding 取 80 条，BM25 取 20 条，再进行 RRF 融合。这种方式比修改公式更容易调试。



    RRF 并不是复杂的算法，却在现代搜索和 RAG 系统中被广泛使用。它的价值不在于“聪明”，而在于在多信号环境下，提供一种简单、稳健、可控的融合方式。



    只有自己实践才能不断的发现问题，葫芦娃之前的 RAG 做的跟 💩 一样

    人类是个很有趣的生物。前段时间，我的一个朋友给我送了一点甜食，家里人看到都说自己不吃，我也不是很喜欢吃甜食。由于是朋友送的，我还是尝了一点，然后就把甜食都放在那里了，这一放就是好几个月，堆积在我的书桌上。



    今天早上我看书桌有点乱，有了兴致就顺手整理起来了。甜食就被我扔到垃圾桶里了。故事在我把东西扔进垃圾桶开始发生了，家里的人凡是看到垃圾桶那个被我丢弃的甜食，都觉得可惜，但是我一问他们还是说自己不会吃，可以给别人吃。



    人类有趣的事情就在于会觉得浪费可惜，但是哪怕这个东西毫无用处，也没有人会吃，无人会在意。
